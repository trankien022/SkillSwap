# ADR-032 — Final booking confirmation follows successful wallet settlement

**Status:** Accepted. Implementation pending the phases in tasks/payment-boundary-review.md.

**Context.** ADR-018 selects per-module outbox transactions and states that a booking stays pending until its wallet settlement succeeds. Current live-class code instead marks it confirmed before publishing booking.confirmed; wallet-ledger may then reject insufficient credits. Consequently the funded happy-path tests do not establish AC-005 failure behavior. Architecture and ADR-013/014 prohibit solving this with cross-schema SQL or one shared privileged connection. The SRS's literal single-database-transaction wording remains a documented consistency discrepancy; this ADR does not claim distributed writes are one SQL transaction.

**Decision.**

1. Preserve the five existing booking states. A confirmation request keeps the hold Pending and returns confirmed=false until settlement has actually completed. The owner/expiry guards from phase A remain mandatory. Balance displayed by a mobile client is feedback, never payment authority.
2. Extend the canonical bookingConfirmedSchema with a `settled` discriminator, default false for historical request messages. Retain booking.confirmed as the legacy settlement trigger with settled=false, documenting this compatibility meaning. After the actual final transition, emit the same existing event family with settled=true. Add classId as planned in ADR-031. Wallet consumes only request messages; notification/reminder consumers accept only final settled messages. No event names are invented outside the approved contract families.
3. The wallet's successful learner_debit and its wallet.transaction.completed outbox event share the wallet transaction. Extend that approved event contract with bookingId correlation required for booking_payment. Use the persisted debit transaction ID as the durable outcome identity, including idempotent replay; an existing debit must be able to ensure its outcome exists. Insufficient balance commits neither ledger effects nor a successful outcome.
4. Live-class consumes the successful correlated outcome idempotently, verifies account/amount/booking identity, and under its own transaction marks an eligible pending booking Confirmed and publishes settled=true. Room access and confirmed read projections remain unavailable before that transition. Duplicate outcomes do not create another final confirmation.
5. If a hold expired or its class/booking was cancelled before a late settlement outcome arrives, do not confirm it. Publish the existing booking.cancelled compensation request from the same local transaction. Wallet's existing unique refund constraint refunds once; a cancellation received before payment must not prevent this later compensation. Test duplicate, reordered, delayed and replayed messages, including cancellation/expiry races.
6. Mobile shows processing/reconciliation while pending, and distinguishes booking confirmation from verified debit evidence. T09 remains incomplete until insufficient funds, timeout, duplicate/cancel/expiry and funded paths have persisted integration evidence. Notifications must never announce final booking success from a request-phase message.

**Consequences.** Seven schema owners and TypeORM per-module transactions remain intact. The business outcome converges through durable outbox messages, with temporary processing states visible. Source contracts, producers, consumers and acceptance evidence must change together. The literal SRS transaction discrepancy must remain explicit in final acceptance rather than being hidden behind green tests.

**Verification.** Focused request/owner/expiry tests; wallet transaction rollback and outcome atomicity; consumer restart/duplicate tests; funded and insufficient-credit strict Gateway probes; forced late settlement with one refund and no room grant; full pnpm verify; native processing/final outcome evidence. Existing funded payment E2E evidence is retained with its limited scope.
